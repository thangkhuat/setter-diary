- (direction) Source: docs/product-brief.md (Oct 5 2026). Input is rich; extract directly, no elicitation. Slug setter-diary derived from product name.
- (decision) Kernel scope = brief's Version 1; 'Later' items become non-goals for this spec.
- (capability) CAP-1: Setter and teammates have accounts, log in, and are bound by per-user permissions from v1 (app holds teammates' data).
- (capability) CAP-2: Setter maintains the team roster; roster members are the selectable hitters.
- (capability) CAP-3: Editable set-type list, seeded with high outside, back set, quick, shoot, pipe.
- (capability) CAP-4: Sets are grouped under a session carrying date, drill-or-match, notes.
- (capability) CAP-5: Courtside one-tap logging of a set: hitter, set type, pass quality (good/OK/poor), rating 0-3; large buttons; may be entered by setter or a teammate on the bench.
- (capability) CAP-6: A hitter can rate sets they received on the same 0-3 scale; stored separately from setter rating so the gap is a signal.
- (capability) CAP-7: Consistency trend view: weekly average rating and % hittable (2 or 3), filterable by set type; answers goal 1 (high outside consistency week over week).
- (capability) CAP-8: Hitter x set type grid: average rating per combination with change since a chosen date (e.g. 1.4 -> 2.2 since August).
- (capability) CAP-9: Personal dashboard per player: own progress (v1 = quality of sets received) plus the setter's progress.
- (constraint) Rating is outcome-based 0-3 defined by what the hitter could do (3 full swing, 2 attack with adjustment, 1 free ball/tip only, 0 unhittable or setting fault); never 'how it felt'.
- (constraint) Accuracy must come from design, not video; no feature may require video to function.
- (constraint) Per-set entry must be completable courtside between drills: large one-tap targets, no typing.
- (constraint) Setter and hitter ratings of the same set are kept distinct, never merged or overwritten.
- (constraint) Views emphasise multi-week trends over single sessions (sessions are noisy).
- (constraint) Access control is part of the v1 design, not retrofitted.
- (constraint) v1 data scope: one setter, one team.
- (decision) Companions: set-log-model.md (fields, rating scale, accuracy practices), access-matrix.md (who logs/views what), progress-views.md (v1 view definitions + deferred views).
- (assumption) 20-set sampling block and monthly filmed calibration are user practices in v1; app does not enforce or support them (video-linked calibration is Later).
- (assumption) Setter-vs-hitter gap is captured in v1 data but only displayed once the comparison view ships (Later).
- (assumption) 'Week' for trend aggregation = calendar week.
- (question) Who logs during training: the setter, or a teammate on the bench? (brief) If a teammate, they need permission to log on the setter's behalf.
- (question) Phone-first web app or native mobile app? (brief)
- (question) Should the setter see each hitter's individual ratings, or only averages? (brief)
- (question) One team only, or can other teams sign up? (brief)
- (question) Hitting stats in a later version? (brief; v1 excludes them)
- (question) Since teammates view the setter's progress, does the hitter x set type grid show every hitter's name and numbers to all teammates, or only rows for the viewer?
- (question) How does a hitter find and rate sets they received, and is there a time window after which rating closes?
- (question) Target logging time per set (e.g. under N seconds) to make CAP-5 success testable?
- (question) Must logging work offline / on poor gym connectivity?
- (question) Teammates' personal data: are any players minors, and what consent, data-export and account-deletion rules apply (e.g. GDPR)?
- (assumption) Setter owns roster, set-type list, and session management; brief puts them in scope without naming an owner.
